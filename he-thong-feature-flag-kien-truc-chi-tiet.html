Phân Tích Chi Tiết Kiến Trúc & Luồng Gọi Service

Tài liệu phân tích chuyên sâu về cách thức giao tiếp đa dịch vụ, bản chất dữ liệu gửi giữa Admin Portal & Feature Flag Service, cơ chế bảo mật xác thực, và luồng nghiệp vụ 3 tầng: Super Admin → Seller → End User.

1. Tổng Quan Kiến Trúc 3 Dịch Vụ

Hệ thống áp dụng kiến trúc Decoupled Multi-Tenant Feature Flagging (Tách rời quản trị tập trung và đánh giá cục bộ tốc độ cao). Hệ thống gồm 3 thành phần chính:

Admin Feature Flag Service

Port 8084 (Container)

Dành riêng cho Super Admin quản trị toàn hệ thống. Quản lý danh mục Tenant (Công ty đối tác), danh mục cờ tổng (Master Features), và thực hiện Cấp phép cờ (Licensing / Granting) cho từng Tenant.

Database: admin_feature_flag_db Vai trò: Cấp phép

Feature Flag Service

Port 8081 (Container)

"Bộ não" quản lý cờ trung tâm, tích hợp Togglz Engine. Quản lý trạng thái Bật/Tắt của Seller, lưu trữ các chiến lược nâng cao (Multi-strategy Rules: user, role, IP, release date) và chịu trách nhiệm đóng gói Snapshot để đẩy xuống các tenant.

Database: feature_flag_db Vai trò: Lưu trữ & Snapshot Dispatcher

Tracking Order (Business App)

Port 8082 (VTIT) & 8083 (KMA)

Ứng dụng nghiệp vụ TMĐT phục vụ khách hàng. Mỗi Tenant có một instance chạy riêng (Database riêng). Nhận snapshot từ Feature Flag Service, lưu vào bảng feature_flag_configs và đánh giá cờ tại chỗ (Local In-Memory Evaluation) với độ trễ 0ms.

Database: tracking_order (A/B) Vai trò: Local Execution

3. Admin-Service Gửi "Context" Hay Gửi Gì Sang Cho Feature-Flag?
Câu trả lời chuẩn xác:
Admin-Service KHÔNG GỬI CONTEXT NGƯỜI DÙNG sang cho Feature-Flag Service! Thay vào đó, Admin-Service chỉ gửi DỮ LIỆU CẤP PHÉP (LICENSING / GRANTING).

Dữ liệu Admin-Service Gửi Sang:

Chỉ là các chính sách cấu hình dịch vụ tĩnh giữa Super Admin và Tenant:

  • Thông tin Tenant: Mã tenant (customerCode = "VTIT"), tên công ty, địa chỉ service URL nội bộ (http://tracking-order-a:8080).
  • Cờ cấp phép: isGranted = true/false (Tenant này có quyền sử dụng tính năng "Mua Ngay" hay không).
  • Tín hiệu kích hoạt Apply: Ra lệnh cho Feature Flag Service đóng gói snapshot và đẩy cấu hình.

Vậy "Context" Đến Từ Đâu Và Ai Xử Lý?

Context là ngữ cảnh động của người dùng cuối khi họ đang truy cập app:

  • Ai đang login/request? → Username (ví dụ vtit1, vtit2).
  • Vai trò là gì? → Role (BUYER, SELLER, SHIPPER).
  • IP mạng từ đâu? → Client IP (172.19.0.1 hoặc 127.0.0.1).
  • Thời gian nào? → Request Time (ngày giờ hiện tại).
  • 👉 Tất cả Context này do chính Tracking Order tự trích xuất từ HTTP Request và Spring SecurityContextHolder tại chỗ, không cần ai gửi từ bên ngoài!
Admin-Feature-Flag-Service • FeatureFlagServiceClient.java Java 
// admin-service chỉ gửi quyền sở hữu cờ (isGranted), KHÔNG hề có username/IP của người dùng:
public boolean syncCustomerFeatureFlag(String customerCode, String flagName, boolean isGranted) {
    String url = featureFlagServiceUrl + "/api/v1/flags/customers/" + customerCode + "/features/" + flagName;
    CustomerFeatureFlagSyncReq req = CustomerFeatureFlagSyncReq.builder()
            .isGranted(isGranted) // Chỉ gửi cờ Super Admin cấp phép
            .enabled(isGranted)
            .build();

    ResponseEntity<String> response = restTemplate.exchange(url, HttpMethod.PUT, new HttpEntity<>(req, headers), String.class);
    return response.getStatusCode().is2xxSuccessful();
}
4. Tại Sao Ở Feature-Flag Fix Cứng Username/Password Nhưng Khi Dùng Với Tracking Order Thì Không Cần Login?

Đây là thắc mắc rất thú vị! Câu trả lời nằm ở 2 thiết kế kỹ thuật độc lập trong mã nguồn:

1
Lý do 1: Cấu hình Spring Security cho phép mở cổng REST API công khai
Trong file SecurityConfig.java của feature-flag-service, cặp tài khoản fix cứng admin / 123456 được sinh ra CHỈ ĐỂ BẢO VỆ GIAO DIỆN WEB của thư viện Togglz (/togglz-console/**). Còn lại, toàn bộ đường dẫn REST API /api/v1/flags/** được cấu hình .permitAll():

    .requestMatchers("/api/v1/flags/**").permitAll() 
    // Chỉ khóa giao diện Web Togglz Console trên trình duyệt:
    .requestMatchers("/togglz-console/**").hasRole("FEATURE_ADMIN")

2
Lý do 2: Kiến Trúc Đẩy Cấu Hình Cục Bộ (Decoupled Snapshot Pattern)
Khách hàng (hoặc app di động/web) khi dùng Tracking Order hoàn toàn không bao giờ gửi request sang Feature Flag Service:
  • Feature Flag Service chỉ đóng vai trò "người giao hàng": Khi có thay đổi, nó chủ động gửi 1 HTTP POST kèm mã bí mật nội bộ X-Internal-Token sang Tracking Order qua endpoint /api/v1/feature-flags/sync.
  • Tracking Order nhận hàng, lưu vào bảng feature_flag_configs ngay trong cơ sở dữ liệu MySQL của chính nó.
  • Khi user vtit1 hay vtit2 đăng nhập, Tracking Order đọc ngay từ DB nội bộ của mình. Vì là giao tiếp nội bộ trong cùng 1 process, tốc độ là 0ms và hoàn toàn không cần đăng nhập vào Feature-Flag-Service!
5. Toàn Bộ Quy Trình 3 Tầng: Super Admin → Seller → End User

Mô hình phân cấp quản trị cờ 3 tầng giải quyết bài toán: Super Admin kiểm soát bản quyền bán gói phần mềm, Seller tự do bật tắt kinh doanh trong phạm vi được cấp, và End User trải nghiệm tính năng theo đúng luật:

T1
TẦNG 1: Super Admin Cấp Quyền Cho Tenant (Licensing)
Super Admin đăng nhập vào Admin Portal, chọn Tenant Viettel Software (VTIT) và bật cấp quyền cho 2 cờ: BUY_NOW và ORDER_DETAIL.
  • Admin Service gọi PUT sang Feature Flag Service: lưu is_granted = true vào bảng customer_feature_flags.
  • Cờ nào không được cấp (như PRICE_INCREASE): is_granted = false.
FeatureFlagServiceImpl.java • Lưu quyền sở hữu cờ Java 
if (request.getIsGranted() != null) {
    customerFeatureFlag.setIsGranted(request.getIsGranted()); // Super Admin cấp phép
}
T2
TẦNG 2: Seller Quản Lý Cờ & Thiết Lập Chiến Lược (Seller Control & Rules)
Chủ shop (Seller của Viettel Software) đăng nhập vào Seller Console:
  • Seller chỉ nhìn thấy 2 cờ được Super Admin cấp là BUY_NOW và ORDER_DETAIL. Cờ PRICE_INCREASE bị ẩn hoàn toàn khỏi màn hình.
  • Seller chủ động gạt tắt ORDER_DETAIL → enabled = false.
  • Với cờ BUY_NOW, Seller bật enabled = true và bấm Edit để thêm chiến lược:
    → Chọn loại: Users by name (mã users_by_name).
    → Chọn danh sách người dùng: vtit2.
  • Seller bấm nút "Apply to Viettel Software".

T3
TẦNG 3: End-User Đăng Nhập & Đánh Giá Chiến Lược (Runtime Evaluation)
Khi người dùng thực hiện đăng nhập vào ứng dụng web của Viettel Software:

Trường hợp user "vtit1":

  1. Đăng nhập thành công, Spring Security lưu auth.getName() = "vtit1".
  2. Hàm evaluateAll() kiểm tra cờ BUY_NOW.
  3. Cờ này có rule users_by_name: "vtit2".
  4. So khớp: "vtit2".equalsIgnoreCase("vtit1") → FALSE!
  5. Kết quả trả về response: "BUY_NOW": false.
  6. Giao diện: Nút Mua Ngay bị ẩn đi!

Trường hợp user "vtit2":

  1. Đăng nhập thành công, Spring Security lưu auth.getName() = "vtit2".
  2. Hàm evaluateAll() kiểm tra cờ BUY_NOW.
  3. Cờ này có rule users_by_name: "vtit2".
  4. So khớp: "vtit2".equalsIgnoreCase("vtit2") → TRUE!
  5. Kết quả trả về response: "BUY_NOW": true.
  6. Giao diện: Nút Mua Ngay hiển thị nổi bật!
FeatureFlagConfigServiceImpl.java • Hàm đánh giá Strategy tại Tracking Order Java 
private boolean evaluateStrategy(String strategyId, Map<String, String> params) {
    return switch (strategyId.toLowerCase(Locale.ROOT)) {
        case "username", "users_by_name" -> {
            String users = params.getOrDefault("users", "");
            String currentUser = getCurrentUsername(); // Lấy username từ SecurityContext
            if (!hasText(currentUser) || !hasText(users)) yield false;
            yield Arrays.stream(users.split("[,\\s]+"))
                    .map(String::trim)
                    .anyMatch(u -> u.equalsIgnoreCase(currentUser));
        }
        // Nếu không khớp rule nào hoặc strategy không hợp lệ:
        default -> {
            log.warn("Unknown strategyId '{}' - treating as disabled", strategyId);
            yield false; // An toàn bảo mật: Chặn không cho kích hoạt tự do
        }
    };
}
